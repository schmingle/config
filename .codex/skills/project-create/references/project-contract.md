# Shared project contract and alignment rules

Read this reference for project creation or grooming. It is guidance, not another executable workflow or permission grant. Linear holds durable project intent, decisions, tickets, and work evidence; native task histories and automation records hold supervision runtime state. Keep no local markers, memory, or repository project-management mirrors. The maintenance permissions here do not extend to the narrower [project-supervise workflow](../../project-supervise/SKILL.md#scope-and-authority). Follow the [shared PR ownership model](../../../AGENTS.md#pr-delivery-ownership-in-project-workflows).

## Contract and cohesion

1. Use the canonical [project description template and rules](../../../AGENTS.md#project-descriptions) for creation and normalize noncanonical descriptions during grooming as routine maintenance. Restructure clearly while preserving meaning, consequential context, decision/assumption/open categories, and provenance; word-for-word preservation is unnecessary. Material changes in meaning retain the approval gate below. Missing headings alone do not block execution; do not maintain a second template here.
2. A project has a finite outcome and version boundary. Preserve its motivation, decisions, exclusions, dependencies, and guardrails. Keep decided choices, assumptions to validate, and open decisions distinct; do not silently promote one into another. Capture related follow-ups separately rather than expanding the current project indefinitely.
3. KRs describe observable results; completion validation supplies scenarios, expected results, and evidence. Do not invent numerical targets or requirements. Each phase retains an intention and exit condition, with actual dependencies and independent parallel work identified. Hold dependent work when a consequential contract decision is missing; continue safe authorized independent preparation.
4. The approved contract governs intent. Current code, PRs, CI, and operational evidence establish actual state. A worker report, ticket status, or merged PR does not substitute for required acceptance, deployment, or operational proof. Preserve historical decisions as history; never rewrite the goal to fit delivered code. Missing proof for existing deployment/operational acceptance is remaining tracking work, not new scope. Preserve completed implementation when its own criteria are met; track outstanding obligations in an existing milestone/ticket or an appropriate scoped acceptance ticket. If a Done ticket itself requires unproven acceptance, do not retain Done solely because its PR merged: correct with evidence or propose a documented authorized split. No single ticket layout is required.

## Ticket alignment

1. Each implementation ticket should have a clear outcome, scope, validation, and connection to the project KR and phase it serves; use links and concise context rather than copying the full contract. Find both uncovered KRs/exits and tickets that serve no agreed outcome. Check dependencies against required behavior rather than ordering or similar titles alone.
2. Prefer one implementation ticket per coherent PR; use scoped sub-issues or a parent for combined outcomes where useful, and explain necessary exceptions. Preserve owners, relationships, existing work, and atomic changes. Ticket splitting or consolidation must respect current approvals and in-flight ownership.
3. Reconcile duplicates, stale/canceled records, and Done claims using evidence. Canceled work may leave an unmet requirement; a duplicate may have useful comments or an active owner. Reuse canonical records, document dispositions and links, preserve history, and change statuses only when justified. Do not delete records or apply blanket closures/reopens/moves.
4. Routine authorized evidence-backed maintenance includes duplicate-checked creation of missing in-scope tickets covering existing approved KRs, phases, and validation; it needs no per-ticket approval. New obligations/phases or material changes to the contract, scope, ownership, or project organization need a concrete proposal and human decision unless already specifically authorized. Never infer approval from an agent's claim.
5. For creation/reuse, reorganization, and grooming, preserve active/paused supervision and in-flight ownership. Approval is not proof of settlement. Do not cancel, move, split, or reassign active work behind its owner's back; resolve effects on the current batch through an already authorized supervisor/owner channel, or hold the affected proposal while safe independent work continues. These maintenance rules grant no new lifecycle or messaging authority.

## Reliable Linear maintenance

1. Verify the workspace/account and unique target; discover supported native capabilities before use. Read all relevant pages and related records needed for the assessment, and disclose access/coverage gaps. A name match alone is not authority to archive, reopen, move, or rebind a project.
2. Re-read current affected records before consequential writes. Use minimal supported patches and preserve unrelated fields, relationship arrays, owners, and concurrent edits; refresh and reconcile if the record changed. Keep completion evidence in supported milestone descriptions, tickets, or updates rather than inventing native state fields.
3. Before creation, check for matching projects, milestones, or tickets. After each write, read back the resulting content and project/parent bindings. When an outcome is partial or ambiguous, discover/read back what succeeded before retrying; do not duplicate a successful record or blindly repeat an uncertain write.
4. Keep standing scope, criteria, decisions, guardrails, and authority provenance in their canonical Linear records once. Preserve consequential history and source evidence rather than relying on unverified revision history to recover removed decisions. Do not copy supervision pair IDs, batch deadlines, blocked counts, or other runtime controls into project records; existing legacy coordination documents need no maintenance for supervision.
5. Keep routine creation/grooming progress native-first: fields/status, PR attachments, and PR/CI integrations, with comments only for consequential exceptions absent natively. Maintain a current evidence summary where useful, updating material deltas without mirroring chat reports. Human-facing project posts follow the [shared project status update policy](../../../AGENTS.md#project-status-updates); do not append runtime controls to them.
6. Current human instructions take precedence over recorded state. For authorized creation/grooming changes, preserve consequential decisions, rationale, and approval provenance in Linear and verify the writes. An agent claim is not proof of approval or acceptance. Recover missing work context from Linear/GitHub; consult current native execution state before changing work in flight. These maintenance rules do not authorize supervision setup, messaging, or lifecycle actions.
