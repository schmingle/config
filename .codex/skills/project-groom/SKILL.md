# Groom a project

Run on explicit human invocation. Creating or reviewing this configuration does not invoke it. Read [the shared project contract and alignment rules](../project-create/references/project-contract.md) before assessing or changing records. Treat Linear as the durable recorded project state and native task histories/automations as supervision runtime state, with no local registry or project-management files. Reconcile consequential chat-only evidence and current human instructions into Linear with provenance/readback before affected continuation; never infer approval or acceptance from agent claims.

1. **Resolve and inspect.** Accept a project URL, ID, or name, or derive a unique project from verified task context. An explicit target takes precedence over stale context; clarify only genuine ambiguity. Verify the intended workspace/account and project before writes. Read the current description, decisions, relevant comments/updates, milestones, complete relevant ticket inventory, and linked code/PR/CI/operational evidence. Inspect relevant current native execution state and active worker ownership; distinguish unknown evidence or incomplete access from verified gaps.
2. **Assess substance and coverage.** Check that the finite outcome, version boundary, KRs, completion proof, and phase intentions/exits form a coherent contract. Trace tickets to the KR/phase they serve and the validation they supply. Identify missing work, unjustified scope drift, duplicates, stale/canceled work whose requirement may remain, and Done claims unsupported by actual acceptance. Include deployment and operational proof where required; a merged PR alone does not complete those obligations. Never rewrite goals to fit the code or invent obligations absent from the contract; follow the shared acceptance-disposition rules for missing proof of existing obligations.
3. **Audit execution readiness.** Read [the execution buckets and readiness criteria](references/execution-readiness.md). Classify each actionable ticket and check its outcome, validation, dependencies, decisions, access, human checkpoints, and executor capabilities against the approved contract. Keep execution responsibility separate from readiness and native ownership. Identify exact gaps without forcing a category or treating every future condition as a current blocker. This assessment performs no acceptance checks or sensitive-access probes merely to establish readiness.
4. **Separate authorized maintenance from decisions.** Normalize noncanonical descriptions into the canonical template as routine maintenance, preserving meaning, decision categories, context, and provenance under the shared rules. Make routine evidence-backed ticket, link, status, and clarification updates, including duplicate-checked creation of missing tickets for approved KRs/phases/validation, within existing authority without per-ticket approval. Present the concrete proposal and obtain any still-needed material contract, scope, ownership, or reorganization decision before applying it; reuse existing approvals. Split implementation work into scoped tickets where practical while preserving coherent atomic changes and the one-ticket/one-PR preference. Do not invent targets, approvals, or business rules, and do not delete records or perform blanket closures. Document duplicate dispositions and retain source links/history.
5. **Respect work in flight.** Preserve paused/active supervision state and in-flight ownership. Do not cancel, reassign, move, or split active assigned work behind its owner's back. Resolve effects on an active batch through an already authorized supervisor/owner channel before changing that work; if that authority or decision is missing, leave the proposal pending and continue independent grooming. This skill does not create a pair, start/resume/pause supervision, or authorize otherwise unapproved messages.
6. **Apply minimally and verify.** Re-read affected records before consequential writes, preserve concurrent changes, and follow the shared recovery rules. Persist compact execution notes in existing ticket descriptions only where useful information is missing; prefer an existing supported equivalent representation. Require no new custom fields, label taxonomy, coordination document, registry, readiness certificate, or handoff token. Read back changes and check contract-to-ticket coverage and current-phase readiness again. Publish material project summaries only when permitted by the [shared reporting policy](../../AGENTS.md#project-status-updates); for tickets use native fields/links/integrations first and reserve comments for consequential exceptions under the shared rules, with evidence and actual IDs. On an unchanged rerun, report briefly without rewriting records or posting another update; distinguish verified completion, implementation, and remaining acceptance work.

7. **Report readiness.** State whether the current phase is ready to start, not ready, or unverified, with exact gaps and their affected work. Give an ordered shortlist of ready candidates, required human checkpoints, and later-phase conditions, using brief actual ticket-ID links. Distinguish work that is ready in principle from work the intended executor can currently dispatch. Keep the report concise; do not duplicate the ticket inventory or create a durable audit ledger. Readiness is an assessment, not a mandatory ceremony or invocation of another skill: do not start supervision, create automations, or require a repeated whole-project audit on every supervisor interval.
