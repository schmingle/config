# Isolated pilot cases

Run a pilot only on explicit human request. Use synthetic records and a disposable checkout for static/dry-run evaluation. Live integrations, chats, automations, paid models, or connected-service writes need separate authorization; editing this skill starts none.

Check observable decisions and resulting artifacts, and report passes, failures, untested behavior, and host limitations separately:

1. **Roster setup and reuse.** Invoke from a current chat with a clear project. Complete the activation gate before heartbeat setup or worker creation. Default to one active assignment; with an approved cap of two, fill both independent slots in the same cycle and reject a third. Verify one nominal 15-minute heartbeat with only `$project-supervise` as prompt and no worker automations. Adopt two known chat IDs and normalize numbered titles without recreating chats/worktrees, restarting batches, or resetting deadlines. A title change or newer duplicate cannot replace a recorded active owner. Resolve ambiguous ownership and uncertain creation results before retrying; uncertain execution occupies capacity. Known old heartbeats may be paused without a historical audit; stale scheduled runs cannot reclaim ownership.
2. **Ordered implementation.** Build distinct per-worker shortlists of next N (default five) from existing priorities/dependencies/phase gates/ownership. Check whole-shortlist independence: if both later contain the same ticket or shared semantic region, hold only that collision and keep independent assigned work moving. Supply more than batch capacity when available. Finish a small first ticket, take the next ready item, and bypass a blocked path for independent work until the 50-minute deadline's cleanup/report reserve. Refresh exhausted/materially changed shortlists without rebuilding them every tick. The implementation worker does not take review-only, coordination-only, deployment, or acceptance chores to fill spare time.
3. **Alignment and quiet Linear.** Test an in-scope implementation error and a missing contract decision. The worker fixes the former in its draft PR and reports the latter without rewriting the plan. Only the worker readies the PR after meaningful local validation and a quick ticket/contract self-check, then comments once with change, PR, validation, and limits. Verify state updates follow existing criteria. A missing ticket, ticket split or revised acceptance criterion requires a labeled planning proposal and concrete human approval before writing or executing it; routine blocker approval and description normalization cannot bypass that gate. At an explicit milestone review gate, present completion evidence and wait for the next plan and execution approval. No inferred deployment/human acceptance, unchanged writes, coordination document, ledger, or checkpoint. The supervisor never changes PRs; review/CI/conflict/merge work belongs to the queue.
4. **Progress and steering.** Exercise useful active work, stalled/off-track work, early idle, and a missing report. Inspect every recorded worker through the same heartbeat. Require the ordered Planning proposals (omit if empty), Blockers, Next steps, Other (omit if empty) report, with important pending decisions restated in full on a later turn. A pending proposal is not a next-step commitment; empty blockers read None. A quiet scheduled response retains the report without an extra notification. Include actual outcomes, evidence-based worker performance, alignment and limits when material. Useful active work continues without repeated nudges; supported focused steering keeps its deadline. One blocked or settled worker does not idle an independent lane; refill eligible capacity before returning. Diagnose early idle from current evidence instead of accepting “batch done” or auditing all history.
5. **Pause/resume.** Prepare a concrete human request before pausing when no useful implementation, read-only preparation, or active wait remains across all lanes. A verified active process still running after four unchanged checks remains monitored or has a verified monitoring handoff; unchanged checks alone do not pause it. Distinguish a written resume condition from a supported wakeup mechanism. Keep runtime state in chat/native records; sufficient human answers resume only after the activation gate, and scheduled ticks cannot override an explicit stop.
6. **Recovery and stop.** Lose a chat, recover approved work/evidence from Linear/GitHub, and recover the roster from current native status without plan rewrites or duplicate active work. Reduce an approved cap from two to one: drain batches without interrupting them or dispatching above the new cap. Stop the project during a Linear outage: use supported native controls immediately for both workers and their helpers, and report each actual running/unknown execution separately from heartbeat pause. A lane-scoped stop leaves unaffected authorized work running. Stale ticks restart neither stopped lane. Require the worker's own-chat report with links, checks/limits, blocked work, remaining order, deadline, and settlement; it sends no messages to a supervisor and needs no supervisor identity.
7. **Scope completion.** All PRs authored still leaves queue/deployment/acceptance work. Continue eligible implementation or supervisor read-only preparation: produce the concrete next decision package and identify the execution owner without activating anything. Completion requires the approved criteria and acceptance evidence. No eligible implementation with unfinished tickets reports blocked authoring, not completion; unchanged completed reinvocation creates nothing.
8. **Audit freshness.** Establish readiness for affected work before heartbeat activation/resume, worker creation, or dispatch. Reuse a recent applicable audit, refresh at one hour or earlier on a consequential change, and use current source deltas rather than silence in chat. Check that unchanged incremental runs stay brief, incomplete/failed runs do not advance the completed timestamp or authorize activation, blocking gaps hold affected work, optional improvements do not, and age alone never stops active work or resumes a pause. The single heartbeat prompt remains `$project-supervise`.
9. **Startup decisions and executor fit.** A consequential decision gap holds affected implementation and creates no implementation worker. Permit scoped supervisor read-only preparation of the exact proposal/evidence needed to resolve the gap without declaring affected execution Ready. A fully prepared human decision with no other useful work pauses; independent ready implementation may continue without rewriting the plan.
10. **Inactive versus active prerequisites.** Compare an assigned Todo/Backlog prerequisite with no verified active execution against an identified active authorized process or concrete pending event. The former needs an owner/action and pauses when no useful work remains; the latter supports lightweight monitoring without a worker. Investigate apparent stalls instead of counting checks. Verify current evidence before dispatch, including after interruption; do not duplicate uncertain execution. For escalation, distinguish the own-chat report from observable native notification behavior and report delivery as unverified when no receipt is available.

11. **Shared ownership and helpers.** Assign separate worktrees and disjoint tickets but introduce a shared barrel/fixture change and conflicting browser ports. Require one shared-file owner or serialized edits and separate runtime resources before overlapping work; worktrees alone do not suffice. Account for a ready PR's pending shared changes without editing that queue-owned PR. A bounded helper may work within its owner's active ticket under explicit ownership/isolation; an independent ticket pipeline delegated to a helper is held. Reassignment waits for the prior ticket's owned execution and helpers to settle.

Static/dry-run checks do not prove live scheduling, continuation, cancellation, or delivery.
