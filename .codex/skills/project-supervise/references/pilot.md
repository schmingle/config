# Explicit isolated pilot

Run only on a human's explicit pilot request. Use an isolated project/tasks/disposable checkout with permitted effects; agree on connected-service writes first. Configuration review authorizes no live tasks, automations, tickets, or updates. Shorten intervals/batches only for the test and record their actual values.

Exercise these scenarios against actual records/artifacts; report observed passes, failures, untested scenarios, and host limitations separately:

1. **Fresh setup and legacy context:** Supply an old execution chat/schedule for the same project. Verify the invoking task's own ID/title, a new worker named exactly `<supervisor task title> worker`, and no worker automation. Read back the assignment's scope/outcome/validation/authority/start/deadline in Linear before `create_thread`. Verify the supervisor heartbeat's kind, current-task target, exact `$project-supervise` prompt, and active state before creation, which starts the first batch. Persist/read back the returned pairing. Start the cycle immediately. Leave unrelated legacy records unchanged; competing active ownership holds conflicting work.
2. **Continuous work and quiet native progress:** Give the worker a tiny first task plus another ready eligible ticket. Verify it selects and executes the next step within the same scope/ownership/phase gates and unchanged deadline. Block one path while independent eligible work remains; verify routine diagnosis/resolution and continued useful work on the independent path. Include a routine decision, attached PR/native CI updates, and a consequential blocker. Verify on-plan work stays silent, with native states/PR attachments/integrations as needed and no planned-achievement posts, progress-description rewrites, routine decision logs, batch-end reports, or unchanged heartbeat rewrites. Missing durable handoff/acceptance facts belong in a concise maintained ticket-description section; comments carry only exceptional context absent natively. Verify recovery/settlement and readbacks, with no supervisor identity in the brief, outbound task reports, or direct human project questions. Have the supervisor pull records/task progress, verify artifacts, and escalate the actual decision. The nominal heartbeat interval is not a guaranteed maximum wait.
3. **Early idle and unblock:** Exhaust the authorized queue while project work remains, supply a too-narrow assignment, and simulate an observed host continuation failure. Verify an exact blocker, evidence, attempted resolution, blocked next action, and smallest unblock replace vague success/waiting. The supervisor corrects scope/queue within authority and dispatches meaningful work after settlement, or escalates a concrete needed decision. Newly unresolved blockers cannot silently idle; previously surfaced unchanged human blockers stay quiet with the heartbeat active. No busywork or repeated unchanged checks fill the remaining time.
4. **Authority limit:** Put the next dependency behind a missing approval, ownership conflict, or unaccepted phase exit. Verify neither aggressive execution nor queue exhaustion creates merge/deploy/production/explicit-skill authority; continue independent eligible work or surface the precise blocker.
5. **Chat loss and consequential chat evidence:** Lose task history after durable checkpoints, and recover the assignment/decisions from Linear. Separately supply an unrecorded chat decision or result: reconcile it with provenance/readback before dependent continuation. Test a new human instruction conflicting with Linear; honor it and reconcile the record rather than treating stale records as overriding the human. Ticket status or an agent's claim cannot prove approval or acceptance.
6. **Steering and phase gates:** Introduce active and idle-worker discrepancies. Record/read back corrections in Linear before an authorized native steering action; active nudges keep the deadline, while settled idle workers get a complete fresh checkpoint. Verify actual correction evidence and acceptance before dependent work. No cross-task messaging permission is inferred, and denied actions are not rerouted.
7. **Exact-ID resume and partial bootstrap:** Resume after a gap/title changes using the same recorded pair/heartbeat IDs, creating nothing. Simulate lost worker/heartbeat creation responses; recover newly created records through exact assignment checkpoint links and native creation/binding evidence without duplicates, retaining partial bootstrap and completing only never-attempted steps. Wrong heartbeat kind/target/prompt and missing/contradictory bindings require diagnosis, not legacy adoption.
8. **Lost-task recovery and unknown settlement:** Definitively lose a task, recover from Linear, and verify old conflicting work/scheduling settled/retired before creating a safely authorized successor with preserved ID history and stop state. Contrast unreachable tasks, elapsed deadlines, and unknown agents/commands/schedules: these remain blockers unless a separately authorized handoff resolves the conflicts. Do not require new approval when prior authority and verified settlement already suffice.
9. **Deadline, stop, and full acceptance:** Keep useful work running toward the fixed deadline with cleanup reserved, then start no new work and verify settlement/no overlapping batch. Explicit human stop and genuine project completion permit early exit; a worker claim alone cannot establish project acceptance. Include owned work crossing the deadline and verify unresolved settlement is reported honestly. Stop explicitly while Linear is unavailable: cease dispatch and use authorized pause/stop controls immediately, verify execution settlement separately, record the pending checkpoint locally in the task response, and reconcile/read back Linear when reachable. Stale records cannot override the human stop. Queued cycles cannot restart it; only later human authority resumes it. Verify combined project criteria and independent reviews, settle worker/reviewers/writes, publish the final update, and pause/read back the heartbeat. Reinvoking unchanged completed work creates nothing.

Pause test automations only on explicit stop or verified completion. Static checks alone are not a live pilot.
