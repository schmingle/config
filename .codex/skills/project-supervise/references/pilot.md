# Isolated pilot cases

Run a pilot only on explicit human request. Use synthetic records and a disposable checkout for static/dry-run evaluation. Live integrations, tasks, automations, paid models, or connected-service writes need separate authorization; editing this skill starts none.

Check observable decisions and resulting artifacts, and report passes, failures, untested behavior, and host limitations separately:

1. **Pair setup and reuse.** Invoke from a new current chat with a clear project or explicit target. Select this supervisor without another adoption question. Verify its nominal 15-minute heartbeat has only `$project-supervise` as prompt, and the exact-title compatible worker has no automation. Among eligible exact-name duplicates, reuse the most recently active task rather than an older recorded match. Preserve an already active batch; skip busy/wrong-name workers. Inspect ambiguous creation results before retrying. Known old heartbeats may be paused without a historical audit; stale scheduled runs cannot reclaim ownership.
2. **Ordered implementation.** Build next N (default five) in the supervisor chat from existing priorities/dependencies/phase gates/ownership. Supply more than batch capacity when available. Finish a small first ticket, take the next ready item, and bypass a blocked path for independent work until the 50-minute deadline's cleanup/report reserve. Refresh exhausted/materially changed shortlists without rebuilding them every tick. No review-only, coordination-only, deployment, or acceptance chores fill spare time.
3. **Alignment and quiet Linear.** Test an in-scope implementation error and a missing contract decision. The worker fixes the former and reports the latter without rewriting the plan. Publish only after meaningful local validation and a quick ticket/contract self-check, then comment once on the worked ticket with change, PR, validation, and limits. No published PR means no comment; later summaries need a useful material authoring update. No other Linear writes, repeated unchanged comments, coordination document, ledger, or checkpoint. Existing legacy documents remain untouched. Review/CI/conflict/merge work belongs to the queue.
4. **Progress and steering.** Exercise useful active work, stalled/off-track work, early idle, and a missing report. Each supervisor invocation reports project progress AND evidence-based worker performance, actual outcomes/links/checks/limits, alignment, remaining work/waits, action or why none, and next/escalation. Useful active work continues without repeated nudges; supported focused steering keeps its deadline. Diagnose early idle from current evidence instead of accepting “batch done” or auditing all history.
5. **Pause/resume.** With no independent authoring, a human-only blocker pauses immediately. External/queue waiting starts count zero, then pauses on the fourth subsequent unchanged scheduled check. Manual checks/missed ticks do not increment; real progress/resolution/human resume resets. Keep runtime state in task history/native records. A sufficient answer here resumes a blocker pause automatically; scheduled ticks/unrelated answers cannot override explicit stop.
6. **Recovery and stop.** Lose a task, recover approved work/evidence from Linear/GitHub, and select an available pair from current native status without plan rewrites or duplicate active work. Stop during a Linear outage: use supported native controls immediately, and report actual running/unknown execution separately from heartbeat pause. Require the worker's own-chat report with links, checks/limits, blocked work, remaining order, deadline, and settlement; it sends no messages to a supervisor and needs no supervisor identity.
7. **Scope completion.** All PRs authored still leaves queue/deployment/acceptance waits. Apply blocked-wait policy to relevant queue work. Once no relevant authoring/queue waiting remains, pause and distinguish authoring-scope completion from full project completion. Do not deploy or assign acceptance work to manufacture a completed project. Unchanged completed reinvocation creates nothing.

Static/dry-run checks do not prove live scheduling, continuation, cancellation, or delivery.
