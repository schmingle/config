# Explicit isolated pilot

Run only on a human's explicit pilot request. Use an isolated project/tasks/disposable checkout with permitted effects; agree on connected-service writes first. Configuration review authorizes no live tasks, automations, tickets, or updates. Shorten intervals/batches only for the test and record their actual values.

Exercise these scenarios against actual records/artifacts; report observed passes, failures, untested scenarios, and host limitations separately:

1. **Current-chat setup without a handoff audit:** Explicitly invoke from a new chat while Linear names an old supervisor. Verify this chat becomes supervisor without a replacement/adoption question or reconstructing historical task/child/command state. Pause an already known old project heartbeat as normal housekeeping, but do not make exhaustive discovery or retirement proof a setup gate. Record current ownership, use an available exact-name worker or create one, and read back the compact assignment/current-chat heartbeat before initial creation/dispatch. An old queued heartbeat exits instead of reclaiming ownership. A direct human invocation resumes a prior stop; scheduled invocation cannot. Actual known active work must not receive a duplicate batch.
2. **Oversized ordered queue and quiet Linear:** Supply real approved work materially beyond batch capacity, ordered by project goals, critical path/dependencies, and human priorities. Verify the compact batch references standing rules and the canonical queue without cloning them; temporary limits stay temporary. Finish a tiny first task, then continue with the next eligible item. Block a high-priority path and verify safe independent work continues within scope/ownership/phase gates and the unchanged deadline. Normal Linear status/PR/CI updates need no narrative or routine decision log; comments carry only consequential exceptions. Under the [shared reporting policy](../../../AGENTS.md#project-status-updates), exercise 15-minute checks and material control/batch changes inside two hours of a published update: maintain recovery state without a project post. After two hours, publish one eligible summary of meaningful accumulated project changes, or skip if unchanged. Include a meaningful published edit and an immediate exception when checking the last-publication window; routine edits/comments cannot bypass it. Questions go promptly to the supervisor chat and relevant ticket; routine blockers, pause/stop/resume/handoff/dispatch, and PR/CI changes do not bypass the window. Only an urgent project risk or verified project completion can justify an immediate post, without repeating an unchanged exception. Verify one sentence plus two to four useful bullets, usually under 100 words, with direct verified links and no control metadata or duplicated detail. The batch ends at its cleanup/report reserve rather than an artificially small deliverable; no busywork is invented near project completion.
3. **Early idle and unblock:** Exhaust the authorized queue while project work remains, supply a too-narrow assignment, and simulate an observed host continuation failure. Verify a local final report states the exact blocker, evidence, attempted resolution, blocked next action, and smallest unblock. The supervisor corrects scope/queue within authority and dispatches meaningful work after settlement, or escalates a concrete needed decision. Diagnose a missing report/unexplained early end before dependent dispatch rather than assuming success. Newly unresolved blockers cannot silently idle. Verify useful independent work continues; when none remains and human input is the sole path forward, surface the needed decision and immediately pause/read back the heartbeat. For an external/time-resolvable blocker, discovery starts at zero; four later consecutive scheduled blocked checks without material progress pause it (about one hour at the default cadence). Manual invocations and missed ticks do not increase the count; rewording or repeated checks do not reset it. Material progress, resolved blockers, and explicit resume reset it. Recover the compact count/pause reason/resume action from the maintained Linear coordination document without local state, narrative count comments, or an extra project status post. A sufficient human answer in the supervisor chat resets the count, reactivates and reads back the heartbeat, and continues immediately without a separate invocation or permission; an insufficient answer leaves it paused with the exact remaining gap. An answer elsewhere must reach the supervisor, invoking the skill there if needed. A stale scheduled invocation cannot resume it. Heartbeat pause never proves active worker settlement or overrides explicit stop. No busywork or repeated unchanged checks fill the time.
4. **Authority limit and PR delivery ownership:** Give a broadly approved contract/assignment, create a PR after local implementation validation, then expose risk/review findings and a CI failure. Verify supervisors, workers, and delegates follow the [project PR delivery ownership rule](../../../AGENTS.md#pr-delivery-ownership-in-project-workflows): observe queue-owned risk/review/fix/CI/merge results without dispatching PR specialists, repeating PR review/signoff, repairing published findings/CI, merging, enabling auto-merge, submitting queue execution, or invoking queue skills directly. Triggering the existing PR merge queue automation to run is permitted; execution remains with that automation. Continue independent eligible work and assess combined project/phase/operational acceptance without redoing PR review. Treat queue waiting under existing four-interval blocked/pause and two-hour reporting rules; surface concrete queue failures/exclusions without taking over execution or routinely requesting bypass permission. Also exercise a missing approval, ownership conflict, or unaccepted phase exit; neither aggressive execution nor queue exhaustion creates deployment, production, or explicit-skill authority.
5. **Chat loss and current evidence:** Leave a detailed own-chat report, preserve only consequential decisions/approval provenance/proof/recovery state in Linear, then lose the chat. On first use, move useful current controls/provenance from existing updates into one maintained Linear project coordination document, reusing a suitable document or creating one if absent; read it back before relying on it, without a historical audit or deleting old updates. Recover standing scope, ordered queue, batch controls, and next action without a mirrored report. Keep the document current in place between published summaries; link native ticket/evidence records instead of duplicating them and never append control metadata to a status post. Apply a material evidence delta to one current summary while retaining consequential history/source proof; do not assume revision history preserves removed decisions. Reconcile a new chat-only instruction/result with readback before dependent continuation; current human instructions override stale records. Agent claims/statuses cannot prove approval or acceptance.
6. **Steering and phase gates:** Introduce active and idle-worker discrepancies. Record/read back corrections in Linear before an authorized native steering action; active nudges keep the deadline, while settled idle workers get a complete fresh checkpoint. Verify actual correction evidence and acceptance before dependent work. No cross-task messaging permission is inferred, and denied actions are not rerouted.
7. **Simple reuse and partial setup:** Reinvoke in the same chat and retain the recorded worker/heartbeat when the worker still has the exact required name and is available; a current active batch continues without duplicate dispatch. Change the supervisor title: do not silently rename/reuse a wrong-name worker for the next batch; choose an available exact match or create one. Simulate ambiguous creation responses and inspect native results before retrying, retaining successful setup without duplicates. Keep the heartbeat on the current chat with the exact prompt; prior name/binding history alone must not trigger an approval question.
8. **Missing history and available workers:** Lose old task history but retain Linear scope/decisions/evidence. Verify setup proceeds without historical settlement proof or repeated handoff approval. Reuse a settled exact-name same-project worker from an old supervisor, or a compatible unbound exact-name worker, using straightforward native availability. Skip obvious foreign/unrelated, busy, or wrong-name candidates; use another available exact match or create one. Resolve ordinary candidate selection from current native status, not an exhaustive provenance audit. A genuinely active current batch is preserved, and a real denied operation is reported precisely without rerouting it or inventing a fresh supervisor-choice gate.
9. **Deadline, stop, and full acceptance:** Keep useful work running toward the fixed deadline with cleanup/report reserve, then verify settlement/no overlapping batch. For deadline, early blocker, explicit stop, and completion, require a final report in the worker's own chat covering actual work/links, checks/limits, material findings, blocked/skipped work and attempted unblocks, remaining priority order, stop time/deadline, and owned-work settlement/unknowns. Useful detail is allowed; no report is sent to another task or posted wholesale in Linear, and no direct human project question or supervisor identity is required. Verify the supervisor pulls the report and actual evidence; host interruption may prevent a report. Explicit human stop and genuine project completion permit early exit; a worker claim alone cannot establish project acceptance. Include owned work crossing the deadline and verify unresolved settlement is reported honestly. Stop explicitly while Linear is unavailable: cease dispatch and use authorized pause/stop controls immediately, verify execution settlement separately, record the pending checkpoint locally in the task response, and reconcile/read back Linear when reachable. Stale records cannot override the human stop. Queued cycles cannot restart it; only later human authority resumes it. Verify combined project criteria and independent acceptance assessments using queue-posted PR results, settle worker/acceptance assessors/writes, publish the final update, and pause/read back the heartbeat. Reinvoking unchanged completed work creates nothing.

10. **Supervisor visibility on every invocation:** Exercise active work, unchanged dependency waiting, early idle with independent ready work, no eligible work, a new human blocker, an already surfaced unchanged blocker, verified completion, explicit stop, and tool/verification failure. Each manual/scheduled cycle leaves its own-chat final reply with clear project/worker state, checks/results/actions (or why none), exact blocker/owner/unblock, and next action/resume trigger. Verify ready-queue coverage and actual independent-work/unblock attempts before a whole-project blocked claim; incomplete coverage is explicit and resolved/escalated. New input needs a concrete question/recommendation; unchanged waiting needs no repeated question or external notification. Report the blocked count, heartbeat state, pause reason, and resume action; only the minimal durable count/control update is needed in the maintained Linear coordination document, without a project status post. Unknown verification/settlement is reported honestly; a blocked report cannot substitute for action, and an outage/report must not delay stop controls. Simulate host interruption and surface missing output next cycle without promising guaranteed reporting.

Pause test automations on the blocked conditions above, explicit stop, or verified completion. Static checks alone are not a live pilot.
