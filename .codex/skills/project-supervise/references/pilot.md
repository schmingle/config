# Explicit isolated pilot

Run only when the human explicitly requests a pilot. Use an isolated test project, test tasks, and a disposable checkout with permitted effects; agree on any connected-service writes first. Configuration review does not authorize creating live tasks, automations, tickets, or project updates. Shorten intervals and batches only for this test, and record their actual values.

Exercise these scenarios against observable task/automation records and resulting artifacts:

1. **Fresh setup with legacy context:** Supply an old execution chat and schedule for the same project. Verify the invoking task's own ID/title is the supervisor, a new standalone worker is titled exactly `<supervisor task title> worker`, and the worker receives no automation. The supervisor heartbeat must read back as `kind=heartbeat`, target that invoking task ID, prompt exactly `$project-supervise`, and active before worker creation, which is the first dispatch with a complete batch brief; verify/persist the returned pair before further dispatch, and start the cycle immediately. Legacy records remain unchanged and cannot qualify by project/name/cadence similarity. An active competing supervisor or unsettled writer holds conflicting work.
2. **Exact-ID resume and binding failures:** Reinvoke in the same supervisor, including after a long gap and title changes, and recover only the recorded project/worker/heartbeat IDs without new records. Test a missing recorded worker/heartbeat, wrong heartbeat target/kind/prompt, and contradictory or unverified bindings: diagnose and hold affected dispatch instead of replacing records, adopting legacy flows, or moving to the old task.
3. **Continuation and delivery:** Give the worker multiple safe steps, an empty authorized queue, and a blocker. Observe whether it actually continues, reports early waiting, delivers an immediate question/final report that wakes the supervisor under existing authority, receives mid-run steering, and leaves the supervisor heartbeat active while blocked. A prompt promising continuation is insufficient evidence.
4. **Corrections and phase gates:** Introduce active-batch and idle-worker discrepancies; confirm nudges retain the active deadline while an idle correction gets a full fresh batch after settlement. Require observed correction evidence. A worker claim and Done ticket cannot clear it or unlock dependent work; independent preparation can proceed.
5. **Deadline and settlement:** Include an owned child agent or command crossing the test deadline. Verify cleanup/status reporting, no deadline reset on a nudge, and no new overlapping batch while owned work remains active or unknown. Report unsupported stop controls honestly.
6. **Partial bootstrap, lost responses, and user stop:** Simulate lost worker/heartbeat creation responses. Recover newly created records through verified current supervisor/project binding without duplicates; retain partial verified bootstrap and finish only never-attempted steps. An unrelated same-project legacy record must not satisfy recovery. Stop supervision while work is active; verify the heartbeat pauses, settlement is checked separately, and a queued scheduled invocation cannot restart either. An explicit human resume reconciles the existing pair, reactivates the same heartbeat with readback, and persists the resume.
7. **Full acceptance:** Verify the combined artifacts against all test-project criteria and independent review. Only after worker/child/supervisor-reviewer/write settlement may completion publish its final update and pause the heartbeat with readback. Reinvoke on unchanged completed work and confirm it creates nothing.

Report observed passes, failures, untested scenarios, and host limitations separately. Pause test automations when the pilot is explicitly stopped or verified complete; never present static checks as a successful live pilot.
