# Execution readiness

These are the shared readiness standards: project-init drafts tickets to meet them, and project-audit assesses them after permitted state grooming, or read-only when requested. Classification records intended responsibility; it grants no access or authority, changes no native assignee or owner, and authorizes no deployment or production mutation. Preserve all existing approval and workflow boundaries.

## Execution buckets

1. **Worker — autonomous implementation.** A ready implementation ticket has clear requirements and sufficient access and authorization for a worker to implement, run its meaningful local checks, and mark a self-contained PR ready for review. The author owns these implementation checks.
2. **Worker — human-assisted implementation.** Implementation needs a specified human decision, authentication, approval, or guidance. The worker can prepare independently within its existing authority, stops at the exact checkpoint, and resumes dependent work only after a valid unblock.
3. **Supervisor — autonomous evaluation.** A bounded phase or project outcome evaluation specifies prerequisites, concrete checks, expected results, and evidence. It evaluates the agreed outcome without repeating PR review, changing the plan, or performing operational mutations.
4. **Supervisor — human-assisted evaluation.** The supervisor prepares independent evidence within its authority, but a named person participates in or owns acceptance, usability assessment, or business judgment. The agent does not declare that person's acceptance for them.
5. **Human-only.** A designated human must perform an action or judgment that cannot be delegated. Agents may prepare material only within their own allowed work.

Browser use or sensitive access alone does not make a ticket human-assisted; identify the actual human step that is needed. If responsibility is ambiguous or no bucket fits, record the gap and decision needed instead of forcing a category. A scoped initiative's parent ticket can link categorized children without a fabricated executor assignment; phases use native milestones as defined in the [shared contract rules](project-contract.md#contract-and-cohesion).

## Readiness standards

1. **Contract and scope.** Trace actionable tickets to approved KRs, phases, and exits; expose uncovered obligations and work without an agreed purpose. Each ticket needs an intended outcome, bounded scope, and meaningful acceptance/validation. Prefer one coherent PR per implementation ticket when practical, retaining justified exceptions and existing ownership rules.
2. **Evaluation proof.** Evaluation tickets define a result to establish and the checks, expected results, evidence, and prerequisites that establish it. Do not create a duplicate checklist of implementation work; implementation checks stay with their implementation ticket. Human acceptance remains with its designated person.
3. **Human checkpoints.** For assisted work, identify the checkpoint, who supplies which decision/input/approval/authentication, when the agent stops and before what action, and what preparation can proceed independently. Human-only work names its owner and concrete action or judgment. Missing owners or unsettled current-phase decisions about intended outcomes, behavior, or scope are gaps, even when listed as human checkpoints; they are not implied agent discretion. A bounded decision task naming the person, question, and required result can itself be ready human work while dependent implementation remains gated.
4. **Dependencies and access.** Check real prerequisite behavior, order, phase exits, needed tools/access, and approval boundaries from available facts, not ticket status alone. Distinguish missing evidence from a verified blocker. Do not test sensitive access or perform acceptance merely to label work ready.
5. **Executor fit.** Assess each ticket against its intended executor's responsibilities, capabilities, access, authority, and human checkpoints. For agent work, use the actual workflow instructions, not the bucket name alone. All five buckets are valid; human execution or the absence of autonomous worker work is not itself a finding. Flag unclear ownership/checkpoints or an actual mismatch between the assigned executor and required work, not merely work outside the project worker's scope.
6. **Readiness and timing.** Keep execution responsibility separate from blockers and dependency state. The intended executor must be able to start current work without redefining goals, changing scope, or recovering missing consequential decisions. Later phases may remain broader when their prerequisites, open decisions, and point of resolution are explicit. Distinguish the plan's structural readiness from work startable now by each intended executor; a Ready project with no eligible implementation does not authorize implementation-only supervision. An inactive prerequisite is a blocker, not evidence that time or an external process will resolve it. Unfinished evaluation with clear checks is remaining work, not a planning defect; dependencies determine what can start now.
7. **Reducing human work.** Look for meaningful ways to reduce human effort within existing permissions: recommend delegating the whole ticket, agent execution with a specific human checkpoint, or a useful agent-owned portion. Apply any resulting plan amendment only under the [plan approval rule](project-contract.md#plan-and-state-permissions). Prefer a worker when the work fits its scope. State what the agent would do and what remains with the human. Report these as optional improvements, not readiness gaps; avoid unnecessary splits or artificial PRs.

When writing tickets, keep concise execution notes with the ticket's outcome and validation when useful: bucket, prerequisites, human checkpoint/preparation, and material access or authority limits. Do not repeat information already clear in the ticket or supported equivalent records. Record facts and unresolved gaps accurately; a bucket is neither reassignment nor permission to reorganize work.
