# Standalone supervision capabilities

Check these requirements when `/project-supervise` is explicitly invoked, using the tools and connector documentation actually exposed in that Claude session. This reference is not a tool implementation, permission grant, or instruction to execute a pilot. Do not infer desktop APIs from their names in the Codex counterpart, an installed CLI, or another chat's authentication.

## Required controls

1. **Linear and repository evidence.** Read the intended Linear workspace/account, contract, milestones, tickets, relationships, and relevant updates; inspect the intended repository and current PRs through available authorized interfaces. State coverage gaps. Use permitted minimal writes only under the [shared plan and state permissions](../../project-init/references/project-contract.md#plan-and-state-permissions).
2. **Independent session identity and inspection.** Identify this persistent supervisor session by stable ID and current title. List and read standalone worker sessions, including identity/title, repository/worktree, current activity, recent output, and settlement. A session must retain its own history and remain distinct from the supervisor's subagent lifecycle. Unknown active execution blocks overlapping dispatch.
3. **Standalone creation and steering.** Open an independent worker session in a verified isolated Git worktree, supply an assignment, and send authorized follow-ups to the existing worker without creating another batch or resetting its deadline. Inspect uncertain creation/dispatch outcomes before retrying. Reuse must preserve current model settings and active work. Do not assume Codex `create_thread`, `read_thread`, or `send_message_to_thread` exist in Claude.
4. **Recurring supervisor invocation.** Create or reuse a schedule that demonstrably invokes this same persistent supervisor with exactly `/project-supervise`, nominally every 15 minutes; inspect its binding, active/paused state, and identity, and support pausing/resuming it. Verify lifetime and host requirements. A reminder to the human, a scheduled new unrelated chat, or an in-process timer that cannot survive the needed session lifetime does not meet this contract. Do not assume Codex automation fields, APIs, or automatic recovery exist.
5. **Stop and settlement.** Pause the schedule and stop the worker's owned execution through supported authorized controls without depending on Linear availability. Inspect actual worker, agent, command, and pending-write states. Pausing a timer, issuing a stop request, or reaching a deadline does not prove settlement. Report running or unknown work accurately.
6. **Handoff when needed.** For a compatible existing worker in a shared checkout, move its session and work to an isolated worktree only through verified supported controls. Inspect completion and the returned destination identity/path. If no safe handoff exists, hold repository work and ask for the specific manual move; do not create a duplicate worker to bypass it. Do not assume Codex `handoff_thread` or `get_handoff_status` exist.

Use connected session/scheduler controls only when their actual schemas and returned evidence establish the required behavior and authority. An available tool name alone is insufficient. Native Claude `Agent` creates subagents and is the interface for separately authorized subagent delegation; it is not a standalone-worker or cross-session-control API. Launching nested CLI processes or repurposing subagents does not silently replace missing session/scheduler controls.

## Capability gap handling

1. **Before activation or dispatch:** when a required control is absent or unverified, leave the affected heartbeat and worker dispatch inactive. Complete a safe current audit/status assessment within available access and report the exact unsupported operation, why it blocks this workflow, and any existing work whose execution is unknown. Do not create a worker simply to test the integration.
2. **Concrete fallback:** ask the human to connect a service that supplies the missing standalone-session/scheduler controls, or manually perform the named action and return verifiable identity/state evidence. While unavailable, the human may re-invoke this chat for another bounded audit/status check; that is manual monitoring, not active recurring supervision. A one-off implementation task or subagent workflow requires an explicit choice of that changed execution model and its own scope; do not start it automatically.
3. **Partial setup or lost controls:** retain successful session/scheduler records, inspect uncertain outcomes, and use any still-supported stop/pause controls when required. Report exactly what is active, paused, running, or unknown and what the human must stop or verify manually. Do not claim a heartbeat is paused or execution settled without evidence; do not dispatch overlapping work.
4. **Authorization and tool denials:** describe the actual denial separately from an unavailable capability. Do not switch transports to bypass it, create shell cron/launchd jobs, install services, change global permissions, write runtime registries, or send external messages as a workaround. Preserve explicit stop and outbound confirmation gates.

Static checks of these files establish links and protocol consistency only. They do not prove that any current Claude environment supplies standalone sessions, cross-session messaging, recurring delivery, or cancellation.
