# Isolated pilot cases

Run a pilot only on explicit human request. Use synthetic records and a disposable checkout for static/dry-run evaluation. Live integrations, chats, automations, paid models, or connected-service writes need separate authorization; editing this skill starts none. Apply [the capability requirements](capabilities.md) first; synthetic fixture results never establish live connector support.

Check observable decisions and resulting artifacts, and report passes, failures, untested behavior, and host limitations separately:

1. **Pair setup and reuse.** Invoke from a new current chat with a clear project or explicit target. Select this supervisor without another adoption question. Complete the activation gate before heartbeat setup or worker creation. When implementation is ready, verify its nominal 15-minute heartbeat has only `/project-supervise` as prompt, and the exact-title compatible worker has no automation. Among eligible exact-name duplicates, reuse the most recently active chat rather than an older recorded match. Preserve an already active batch; skip busy/wrong-name workers. Inspect ambiguous creation results before retrying. Known old heartbeats may be paused without a historical audit; stale scheduled runs cannot reclaim ownership.
2. **Ordered implementation.** Build next N (default five) in the supervisor chat from existing priorities/dependencies/phase gates/ownership. Supply more than batch capacity when available. Finish a small first ticket, take the next ready item, and bypass a blocked path for independent work until the 50-minute deadline's cleanup/report reserve. Refresh exhausted/materially changed shortlists without rebuilding them every tick. No review-only, coordination-only, deployment, or acceptance chores fill spare time.
3. **Alignment and quiet Linear.** Test an in-scope implementation error and a missing contract decision. The worker fixes the former in its draft PR and reports the latter without rewriting the plan. Only the worker readies the PR after meaningful local validation and a quick ticket/contract self-check, then comments once with change, PR, validation, and limits. Verify state updates follow existing criteria, project/ticket plan edits require approval, and neither comments nor description normalization bypass that gate. No inferred deployment/human acceptance, unchanged writes, coordination document, ledger, or checkpoint. The supervisor never changes PRs; review/CI/conflict/merge work belongs to the queue.
4. **Progress and steering.** Exercise useful active work, stalled/off-track work, early idle, and a missing report. Each supervisor invocation reports project progress AND evidence-based worker performance, actual outcomes/links/checks/limits, alignment, remaining work/waits, action or why none, and next/escalation. Useful active work continues without repeated nudges; supported focused steering keeps its deadline. Diagnose early idle from current evidence instead of accepting “batch done” or auditing all history.
5. **Pause/resume.** With no independent authoring or verified time-resolvable wait, a human-only blocker pauses immediately. Verified external/queue waiting starts count zero, then pauses on the fourth subsequent unchanged scheduled check. Manual checks/missed ticks do not increment; real progress/resolution/human resume resets. Keep runtime state in chat history/native records. A sufficient answer here resumes a blocker pause automatically only after the activation gate is met; scheduled ticks/unrelated answers cannot override explicit stop.
6. **Recovery and stop.** Lose a chat, recover approved work/evidence from Linear/GitHub, and select an available pair from current native status without plan rewrites or duplicate active work. Stop during a Linear outage: use supported native controls immediately, and report actual running/unknown execution separately from heartbeat pause. Require the worker's own-chat report with links, checks/limits, blocked work, remaining order, deadline, and settlement; it sends no messages to a supervisor and needs no supervisor identity.
7. **Scope completion.** All PRs authored still leaves queue/deployment/acceptance waits. Apply blocked-wait policy to relevant queue work. Zero eligible implementation with unfinished blocked tickets reports blocked authoring, not completion. Once authoring obligations are satisfied and no relevant active queue processing remains, pause and distinguish authoring-scope completion from full project completion. Do not deploy or assign acceptance work to manufacture a completed project. Unchanged completed reinvocation creates nothing.
8. **Audit freshness.** Establish readiness for affected work before heartbeat activation/resume, worker creation, or dispatch. Reuse a recent applicable audit, refresh at one hour or earlier on a consequential change, and use current source deltas rather than silence in chat. Check that unchanged incremental runs stay brief, incomplete/failed runs do not advance the completed timestamp or authorize activation, blocking gaps hold affected work, optional improvements do not, and age alone never stops active work or resumes a pause. The single heartbeat prompt remains `/project-supervise`.
9. **Startup decisions and executor fit.** Use a current-phase implementation ticket missing an outcome/behavior/scope decision. Report Gaps found with the exact question and recommended decision or amendment; create no worker or active heartbeat when nothing independent is ready. Contrast a bounded named human decision task and a project containing only well-specified human/evaluation work: these may be structurally ready, but dependent implementation stays gated and implementation-only supervision stays inactive. Explicit later-phase decisions do not block a clearly assessed independent current-phase item; dispatch only that ready item without rewriting the plan.
10. **Inactive versus active prerequisites.** Compare an assigned Todo/Backlog prerequisite with no verified active execution against a prerequisite with an identified active authorized process or concrete pending event. Pause immediately for the former when no independent implementation remains; for the latter, monitor with no worker and apply count zero plus four actual unchanged scheduled checks. Unknown activity does not authorize activation. A cached Ready verdict alone cannot turn either case into dispatchable implementation.
11. **Claude capability gaps.** With no standalone-session controls, report the missing create/read/message/stop capability, perform only the safe current audit/status assessment, and create no `Agent` replacement worker. With standalone controls but no verified recurring binding, leave recurring supervision inactive and explain manual re-invocation. Reject reminders, unrelated new-chat jobs, and session-only timers as proof of persistent delivery. With a missing handoff, hold shared-checkout repository work without duplicating the active worker. When controls disappear after partial setup, retain known identities, use supported pause/stop operations, and report actual running/unknown work and the exact manual recovery action. An installed CLI or Codex tool name does not establish capability, and a denial cannot be bypassed through another transport.

Static/dry-run checks do not prove live scheduling, continuation, cancellation, or delivery.
